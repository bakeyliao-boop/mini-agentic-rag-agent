# 运行参数、请求组装与预算检查草案 v1

日期：2026-09-12。状态：draft，用户授权继续整理规划材料；参数与实施未批准，模型调用为0。依赖[试运行方案v2](最小试运行方案草案-v2.md)已接受的模型、五例各3次、总预算1元及三条初筛条件。

本轮新增的是可审阅的请求正文及检查步骤，不是评估器实现。五份样例的内容来自现有材料，没有新写题目、标准答案或策略候选。

## 从一次请求看完整过程

读取固定版规则正文和单例input → 核对将发送的正文 → 预留本次费用且核对剩余额度 → 发送一条请求 → 保存原始响应与用量 → 人工核对评价内容。单例重复时重新创建独立输入，不附前次回复。模型只能看到本次规则和该例数据，不能访问目录或调用检索工具。

目前完成前两步的文件样例和静态检查；费用控制、网络发送及响应留存均未实现。由[样例目录](request-draft-v1/README.md)查看实际正文；不将该目录称为已冻结执行批次。

## 参数建议及理由（待确认）

| 参数或客户端行为 | 建议值 | 目的及限制 |
| --- | --- | --- |
| model | deepseek-flash | 型号已接受；官方规划版本V4.1-Flash，实际响应版本未取得。 |
| thinking.type | disabled | 首轮先检查不启用额外思考过程的表现，控制用量；这不是能力足够的保证，更不能外推到其他模式。 |
| temperature | 0 | 减少采样变化，仍通过独立重复检查稳定性，不保证完全确定。 |
| max_tokens | 2048 | 限制单次输出规模；如果截断，按已定口径检查原文并记录未完成，不自动扩大。 |
| stream | false | 首轮收取完整非流式响应，便于保留content、结束标记及usage；不声称比流式更准确。 |
| response_format | text | 沿用自由表达及人工对账，不新增JSON输出格式门槛。 |
| tools / tool_choice | 不发送 | 评估仅审阅给定记录，不让评估器另外取证。 |
| 并发／重试／超时 | 1／0／120秒 | 串行便于预算预留；禁止自动追加请求；超时单列并保守保留预留费用。120秒是规划建议，不是实测性能结论。 |

后3项客户端控制不属于HTTP正文参数，不能把max_retries或timeout塞进请求JSON冒充服务端支持。若后续采用OpenAI兼容SDK，thinking经extra_body传入是SDK写法；最终HTTP正文应是顶层thinking，不再套extra_body。

官方[思考模式文档](https://api-docs.deepseek.com/guides/thinking_mode/)明确默认开启，因此样例显式关闭；该文档也指出temperature在思考模式下不生效，所以仅写temperature=0不能证明运行条件已固定。本轮没有验证参数在实际账号或代理上的生效情况。

[Chat Completions文档](https://api-docs.deepseek.com/api/create-chat-completion/)描述max_tokens、文本输出与结束标记。该页面本轮直接打开超时，官方搜索缓存显示的型号枚举仍为旧名；型号以2026-09-12已成功打开的[更新日志](https://api-docs.deepseek.com/updates/)为依据，参数结构仍待实际接线核验，不用过时枚举推翻已查的型号变更。

## 请求正文必须精确由两部分构成

1. system消息：从统一说明v2的“评价规则正文”提取，到“组织侧使用边界”之前截止，不附完整Markdown说明、修订记录或审核示例。
2. user消息：单例input序列化为JSON字符串。不传case_id、proposed_expected_judgment、reviewer_explanation、human_review、完整cases.json或其他案例。

其余请求字段仅为上表所列模型控制。样例没有认证头或地址；拟用官方Chat Completions入口，实际渠道须在接线时核实，不读取或回显密钥。发送任何请求前，实际请求对象须与已审核样例语义一致并保存快照；客户端若额外注入消息、格式说明、工具或历史，应先处理，不能静默接受。

五份样例不复制成15份相同文件：[manifest](request-draft-v1/manifest.json)仅在组织侧把每例映射到3个预定槽位，建议按CAL-01至05顺序做三轮。该顺序是可审阅的调度建议，不是已执行事件。无论API响应成功与否，发出过的请求都计入尝试，不能自动补齐15条成功结果。

## 预算检查如何设计（尚未实现）

费用预留按当前规划上限计算，每次12000输入tokens、2048输出tokens。高峰未缓存单价按每百万输入2元、输出8元：一次预留0.040384元，15次0.60576元，总预算1元。它是条件预留，不是已证实实际token量。

执行前必须先证明最终请求输入在12000-token预留内：使用适用于所选模型的可靠token计数并计入消息封装，或提供可审阅的保守上界。当前只有字符/字节统计，未做精确tokenizer核验；这一条件未满足时不发请求。不能把任意字节到token比例当作已经证实的硬上界。

每次发送前：核对已发送请求数少于15；记录本次预留；确认“已花费用的可核对保守值＋未结算请求预留＋本次预留”不超过1元。串行执行避免并发预留相互覆盖。额度或用量依据不足时暂停，不以0补齐。

请求完成后，保存usage、响应模型信息和对应单价来源，标为按用量计算的费用；只有独立账单支持时才称实扣。可按全部输入未缓存、高峰单价作保守计算，不预先依赖缓存优惠。若usage缺失或超时，保留该次全部预留并单列费用未知，不能释放额度为零；若无法确认预留覆盖风险，应暂停。

批次结束后分别报告计划15次、实际发送次数、完整评价数、未完成数、明确误判与未判项，以及实扣／计算／未知费用及来源。该报告不应隐藏超时或截断已经消耗的资源。预算上限已获接受，但上述检查未实施，不能声明已有服务端硬封顶。

## 原始响应与解析分开

保存可取得的响应ID、模型/版本字段、结束标记、原始content、usage、时间及错误信息，敏感认证信息不记录。任何后续解析保留与原始回复的对应。没有设置或验证的字段，不补造默认值。

解析失败先看原始回复：原文表达完整可以人工对账，只记解析问题；原文缺失部分才记未完成。已能确认的错误与缺失并列；正确unknown不当漏答。finish_reason=length提示长度相关结束，还需结合上下文和输出限制核对，不能仅凭短文本猜原因。

无论语义失败、解析问题、超时或截断，都不自动重跑或带着正确结果纠正下一次。本轮不允许策略候选生成，所有结果只交组织者对账。
