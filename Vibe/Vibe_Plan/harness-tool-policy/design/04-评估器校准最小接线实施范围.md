## 最小落点与不扩张范围

拟新增一个实现文件：`evaluation/tool_contribution_calibration.py`；拟新增一份对应离线边界测试：`tests/test_tool_contribution_calibration.py`。如目录内实际约定需要调整文件名，在同一职责范围内安排即可，不拆成公共框架或大量模块。

实现文件内部收纳材料校验、有限调度、发送、预算记录和落盘所需小函数。优先用现有httpx依赖发送已审核HTTP正文，避免原Judge的结构化包装注入新格式说明或丢失原始响应；认证仅在获准真实模式中按现有配置方式使用，不回显、不写入请求快照或日志，不修改.env。

默认入口只执行准备检查，不能导入即发送网络请求。真实发送必须显式选择真实模式，且具体批次已得到用户执行授权；本次不预填可直接执行的命令，也不把执行开关等同于授权本身。

结果建议落在`evaluation/results/tool-contribution-calibration/<batch-id>/`的新目录，包含材料版本索引、15个计划槽位、逐次请求快照/状态/原始响应或错误、费用记录及人工对账表。具体文件字段属于实现细节，以可追溯和不覆盖为验收标准，不冻结公共API或数据库schema。

暂不做：修改现有RAG runner；自动语义判分；直接继承策略；加入D02/VAL/REG；建立索引或Langfuse项目；改公共配置或部署依赖；自动续跑、自动改规则、失败后自动再试。

## 一个请求的完整处理约定

### 发送之前

- 准备模式不读取密钥或加载会触发环境副作用的项目初始化，只读取指定规划输入和需要的非敏感元信息。
- 固定本批材料/参照/规则/模型参数及组装方式；核对五份正文哈希、system规则一致性、user与单例input一致性、禁止字段和其他案例未混入。只有文件名或case_id一致不够。
- 原请求正文与本地计数报告中的哈希必须对应；任何输入变化均重新核验并另立批次。计数无需依赖临时目录持续存在，可依据已保存的固定版本证据和原文哈希复核；这些是本地计数，不冒充线上usage。
- 将请求快照、该次槽位和费用预留先持久化。写入失败时不发送请求；不能等整批结束才保存。
- 限制总槽位15和总预算1元；每次保守预留0.040384元（12000输入、2048输出、高峰未缓存单价），未结算的预留不当作可用额度。计价渠道与接受的估算不一致时暂停核对，不自动换模型或服务商。

### 发送及返回之后

- 一次只有一条在途请求，关闭客户端及传输层自动重试；不通过自动重定向、自动重连或封装回退暗中新增推理请求。
- 记录调用开始这一可观察事实，不把本地“准备完成”当成服务端已收到。超时、崩溃或网络异常时，服务端是否执行可能未知，保守占用该槽位和预留；不自动补发。首次版不支持同批自动恢复发送。
- 收到回复先保存原始响应体与可取得的响应ID、状态、结束标记、模型字段和usage，再做可选解析或整理。只选择允许保存的非敏感元信息，不保存认证头。
- 解析失败不能导致原始回复丢失；原始文本完整时可以人工对账，解析问题单列。已确认错误和缺项仍按已接受的三条初筛口径分别记录。
- 原始结果落盘失败、材料变化、预算无法可靠核对等情况，停止后续发送并保留已经有的记录；不覆盖或静默重建原批。

### 费用及对账

usage乘明确单价是计算费用，平台扣费凭据才支持实扣；缺usage、账单或明确用量时标未知，不能填0。超时/缺usage保留整次预留；若无法确认其覆盖风险则暂停。没有已发送请求时，也不能编造API usage对象来表示零。

首次及后续获准请求都可以顺带比较API prompt_tokens与对应本地计数，不另外增加探针。超出12000预留或出现可确认的版本/模式偏离等情况暂停；一般差异原样记录，不把本地计数直接替代usage。

每次与批次末尾输出的只是可对账事实和待人工检查项。三条初筛结论由组织者依据[已接受方案v2](../calibration/2026-09-11-v1/最小试运行方案草案-v2.md)完成；程序不靠标签相等自动宣布模型合格，参照争议仍先复核并按新批次处理修改。

## 怎样验收这段实现

先做一轮完全断开真实模型的离线验收，用可控的假传输/临时输出目录检查。测试只检查边界行为，不把模拟回复当成模型校准结果。

| 场景／反例 | 必须观察到的结果 |
| --- | --- |
| 正常准备五例与15槽位 | 只产生预检材料；无网络请求，case内容和预期文件不改。 |
| 实际请求混入金标、另一个案例、历史回复，或任一材料哈希改变 | 在发送前拒绝，假传输调用数0，说明具体差异。 |
| 达到15槽位或剩余额度不足 | 第16次及越额请求不能发送；现有费用和未结算预留均参与检查。 |
| 开始发送后超时／usage缺失 | 保留已开始/不确定状态、原始错误及预留；不自动重试，费用不记0。 |
| 原始回复完整但解析失败 | 原始回复先保存且可读，解析问题另列，不能直接判模型能力错误。 |
| 输出被截断且已输出部分有明确错误 | 原始文本与结束原因保留；完整性缺失与已确认误判可以并存，不以一个覆盖另一个。 |
| 保存请求失败，或保存响应失败 | 前者不发送；后者停止后续请求。重启入口不能覆盖目录或自动重发状态不明的槽位。 |
| 提供方缓慢分段传输或保持连接 | 验证整体120秒截止的语义；测试缩短等待时间完成验证，不实际阻塞120秒，不误称单次read超时就是整体上限。 |

这是未来代码获准后的离线验收要求，本轮没有写测试或运行这些场景。无需扩大成整仓测试或模型对照实验。

真实运行前还需收口最终整例人审确认记录、参数与批次冻结清单。当前cases.json只有CAL-01已标完整人审；后续确认可有明确的审核侧签收记录，但不能由程序把false自动改成true。此处只是记录待办，不要求重复讲解已讨论的五例。
